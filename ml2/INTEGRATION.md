# Интеграция ML1 из папки ml2

Обновлено 2026-10-18. Рабочая ветка `main`, база этой правки — `8cf0d4c`.
Патч таймаутов уже применён в main (`8cf0d4c`); его файл оставлен для истории
и обратной проверки. Текущая правка касается только скриптов, тестов и документации.

## Границы изменений

Новый сервис находится в `ml2/`, порт **8001**, переменная **ML1_URL**.
Matching другого участника остаётся на **8002**, переменная **ML2_URL**.
`contracts/`, `backend/app`, `frontend`, `ml1/`, `data/rules.json` не изменены.
Кроме `ml2/` изменены только корневые README и .gitignore.

ML работает на Python 3.12.10; интеграционный backend запущен на Python 3.14.7.
Это разные виртуальные окружения. Модели находятся снаружи клона и подключены
через `ML_MODELS_DIR`; веса, данные, кэши и окружения в коммит не входят.

## Контракт и ошибки

`POST /analyze`, multipart `file` → analyze_video → ML1 Observation:

| Внутренний Event | ML1-контракт |
|---|---|
| rule_id + порядковый индекс + начало | id = rule_id:индекс:секунды |
| timecode_sec / first_seen | start_sec |
| max(first_seen, confirmed_at) | end_sec |
| description | description |
| 1–3 JPEG + фактические времена кадров | evidence_frames |

У ML1 Observation нет отдельных полей type/rule_id/confidence. Backend отбрасывает
посторонние поля при разборе Pydantic, поэтому добавление их в JSON не решит передачу
типов. Для текущих проверок rule_id находится в id. Нужен согласованный mapping
наблюдений в утверждённые rule_id участника 4, прежде чем включать matching.

Нулевое число срабатываний возвращает строго `{"schema_version":"1.0","events":[]}`.
Неизвестное/отключённое правило не публикуется. Ошибки не превращаются в пустой 200:
400 пустой файл, 408 таймаут загрузки, 413 размер, 415 формат, 422 декодирование,
503 занятость, 504 бюджет inference, 500 прочая ошибка. Ответов со статусом failed
наш сервис не создаёт. При аварии рабочего процесса `/health` становится 503;
для восстановления нужен перезапуск сервиса.

При пустом whitelist и завершённом perception возвращается обычный HTTP 200:
`{"schema_version":"1.0","events":[]}`, `X-Rules-Enabled: none`.
Заголовков `X-Analysis-Status` и `X-Analysis-Complete` в успешном ответе нет.
Backend принимает ответ и через matching трактует пустой список как `no_violation`.
Это означает «включённых правил нет», а не подтверждённое отсутствие нарушений.
Внутренний диагностический отчёт может по-прежнему отражать недостаточное покрытие
правил; это не является обрывом обработки и не транслируется в HTTP-заголовки.

Заголовки `X-Analysis-Status: partial` и `X-Analysis-Complete: false` передаются
только при реальном таймауте inference, вместе с HTTP 504. Повреждённое видео
и прочие ошибки остаются HTTP-ошибками, без этих заголовков. Отсутствие правил
больше не вызывает `ML1_INCOMPLETE`; настоящие ошибки могут завершать backend job
как failed — их нельзя скрывать пустым ответом. Каталог matching на 8002 также
должен быть настроен: исправление ML1 не устраняет отдельную ошибку RULES_EMPTY.

## Нормализованный MP4 и временная шкала

Backend передаёт `video.mp4`, MIME `video/mp4`, H.264/yuv420p без звука.
Сервис принимает такой файл и декодирует только его видеодорожку локальным PyAV
19.0.1 (BSD-3-Clause). OpenCV остаётся для обработки изображений и JPEG.
Единственный источник времени кадра — `frame.pts * frame.time_base`.
FPS и число кадров не используются для вычисления времени или seek-позиций.
Seek выполняется в time_base видеопотока, с декодированием от ключевого кадра.

VFR и положительный PTS первого кадра сохраняются; пустой ведущий интервал
не заполняется выдуманными кадрами и не сдвигается к нулю. При пропуске PTS
вход отклоняется, вместо подстановки номера кадра / FPS. Evidence содержит
фактические PTS выбранных кадров. Это устраняет прежний случай OpenCV,
когда кадр с PTS 2,0 с получал POS_MSEC=0.

Добавлены синтетические проверки H.264/yuv420p MP4, MIME video/mp4, VFR,
начальной задержки, поворота, JPEG evidence, ошибочных PTS и таймаутов.
Все 141 тест ML2 прошли; pip check ошибок не обнаружил. Ответы настоящего
HTTP-адаптера также переданы текущей функции backend `_request_json` через
локальный MockTransport: успешный пустой ответ принят без ML1_INCOMPLETE,
таймаут остаётся явной ошибкой. Это проверка контракта, без вызова моделей.
Дополнительно полный сервис с реальными локальными RT-DETR/SigLIP обработал
синтетический нормализованный MP4: HTTP 200, events=[], X-Rules-Enabled: none,
без заголовков неполноты. Исходные видео и закрытый набор не использовались.
Исторические замеры времени ниже относятся к v6 до смены декодера.

Backend сохраняет `failed` для настоящих HTTP-ошибок и таймаутов обработки.
Это ожидаемое поведение: ошибку нельзя выдавать за успешный пустой результат.
Пустой список включённых правил теперь является успешным ответом ML1.

## Проверка цепочки

Текущий воспроизводимый запуск — `scripts/run_chain.py`, заглушка —
`scripts/matching_stub.py`, проверка сохранённых ответов — `scripts/check_events.py`.
Команды и параметры: [README.md](README.md#локальная-проверка-цепочки).
Ни один из этих скриптов не включает правила и не меняет perception, роли или якоря.

Новая проверка на Windows выявила существующий блокер `backend/app/media.py`:
обращение к `signal.SIGXFSZ` и запуск `resource.RLIMIT_FSIZE` несовместимы с Windows.
В неизменённом backend и копии с патчем таймаутов одинаково: **176 passed / 36 failed**.
Поэтому исторические успешные замеры ниже не являются подтверждением текущей
полной цепочки на Windows. Текущие результаты: [eval/chain/report.md](eval/chain/report.md).
Исправление нормализации/квот остаётся участнику 3; лимит диска обходить нельзя.

Следующий раздел описывает **исторический транспортный прогон v6**.

Запущены реальный ML1 8001, реальный backend с PIPELINE_MODE=live 8000 и явно
тестовая заглушка `/match` 8002. Использованы только открытые видео 2 и 14.
API-ключ случайный, только в окружении процессов; в файлы и вывод не записан.
JPEG не выводились и не передавались внешним сервисам.

Первый запуск с исходным `data/rules.json` остановился с `RULES_EMPTY`:
видео 2 — 0,78 с, видео 14 — 0,40 с (полный HTTP/poll цикл). До ML1 backend не дошёл.
Это реальная ошибка конфигурации, а не результат «нарушений нет».

В `ml1/outputs/forte_rules_kz.json` уже есть 8 исследовательских правил команды
с источниками. `scripts/prepare_transport_catalog.py` структурно преобразует их
в **игнорируемую** копию `cache/integration/transport_catalog.json`; исходные
файлы не меняются. Сохраняются источник, пункт, условия применимости и исключения.
Отсутствующие реквизиты отвергаются, нормативные ссылки не придумываются.
В копии явно указано `integration_test_only=true`. Применимость каталога и его
публикация в data/rules.json требуют содержательной проверки участником 4.

Повторный транспортный прогон использует RULES_PATH на эту копию, а не подменяет
рабочий каталог. Заглушка matching возвращает no_violation для пустых наблюдений;
для непустых требует известный rule_id из переданного каталога. Она не проверяет
нормы, не заменяет сервис участника 2 и не включена в обычный запуск.

| Видео | Прямой ML1, с | Полная цепочка HTTP/poll, с | ML1 внутри backend, с | Итог |
|---|---:|---:|---:|---|
| 2 | 15.46 | 15.49 | 15.25 | done / no_violation |
| 14 | 49.18 | 50.34 | 50.02 | done / no_violation |

Это тест транспорта с заглушкой matching и пустым whitelist правил. Оба ответа ML1 проверены по текущей JSON Schema; истинность вердикта по видео не проверяется. Модели загружены по одному разу; кэш признаков сбрасывается между запросами, что отражено заголовком X-Input-Cache. Повреждённый MOV вернул HTTP 422, а не пустой успешный ответ. Логи и исходные JSON находятся только в игнорируемом cache/integration_final/.


## Таймауты участнику 3

Исторический [патч](patches/backend-ml-timeouts.patch) уже применён в main
коммитом `8cf0d4c`. `git apply --reverse --check ml2/patches/backend-ml-timeouts.patch`
проверяет это без отмены правок. Прямой `git apply` к main повторно не нужен.
Тесты читают итоговый backend, проверяют read/total ML1/ML2, сохранение ошибок
таймаута и дедлайн задачи ≤295 с. Старые ошибки Windows устранены отдельно
в `20d3f21`: актуальный backend suite — 217 passed; красные результаты выше
относятся к историческому прогону до этого исправления.

До патча ML1/ML2 использовали read=90 с и общий предел HTTP-запроса 120 с.
Исторический тест 285-секундного видео в исходном проекте занял
103,84 с: он уже превышает read=90 с на **13,84 с**. Максимальный бюджет ML1 — 170 с.

В main установлены раздельные лимиты стадий:

| Лимит | До патча | Сейчас | Изменение |
|---|---:|---:|---:|
| ML1 read | 90 с | 180 с | +90 с |
| ML1 полный HTTP-запрос | 120 с | 190 с | +70 с |
| ML2 read | 90 с | 90 с | без изменения |
| ML2 полный HTTP-запрос | 120 с | 100 с | −20 с |

По прямому указанию пользователя ML2 теперь read=90 с / total=100 с;
ML1 остаётся read=180 с / total=190 с. Это лимиты ожидания, а не гарантированные
отдельные бюджеты: 190+100=290 с, ровно JOB_TIMEOUT_SECONDS по умолчанию,
без загрузки, очереди и подготовки. Общий дедлайн включает эти стадии и может
отменить ML-запрос раньше его собственного предела. Для полной суммы максимумов
с загрузкой понадобилось бы более 350 с плюс подготовка, что превышает текущий
потолок; мы не увеличиваем и не обходим его. Жёсткий backend-потолок
295 с в этом изменении не тронут. На видео 2/14 отдельные текущие измерения могут
укладываться в 90 с; это не покрывает весь заявленный диапазон входных видео.

## Запуск для жюри и доступность Linux

Инструкция: [eval/chain/RUNBOOK.md](eval/chain/RUNBOOK.md), единый launcher —
`scripts/launch_chain.py`. Linux: три процесса на хосте; уже исправленный backend
используется как есть (`timeouts already applied`). В старом checkout launcher
применяет патч только к копии в cache; если ни прямая, ни обратная проверка
не проходит, запуск останавливается до изменения файлов. Windows: ML1 8001 и matching stub 8002 на хосте, backend
в локальном Linux-контейнере, ML1_URL/ML2_URL через `host.docker.internal`.
Ключ передаётся только переменной окружения API_KEY и заголовком X-API-Key.

На этом компьютере повторно проверено: `wsl --status` → код 50,
«The Windows Subsystem for Linux is not installed»; `docker --version`
недоступен (команда не найдена), стандартные файлы Docker Desktop отсутствуют.
Linux-прогон видео 2/14 с обновлённым патчем **не выполнен**. Установка и обход
ограничений не предпринимались. Нужен установленный WSL2 с Linux и зависимостями
backend, либо Docker Desktop с работающим Linux engine, либо отдельная Linux-машина.
Dockerfile и межсистемная сеть пока не проверены настоящим контейнерным запуском.

## Воспроизведение проверки

Из ml2, при доступных локальных FFmpeg/FFprobe и уже установленном backend:

```powershell
.venv/Scripts/python.exe scripts/prepare_transport_catalog.py
.venv/Scripts/python.exe scripts/integration_check.py --open-root C:/path/to/data/open --ffmpeg-bin C:/path/to/ffmpeg/bin --models C:/path/to/models --rules-path cache/integration/transport_catalog.json
```

Скрипт поднимает тестовые процессы, вызывает POST /api/v1/analyze, опрашивает job,
проверяет прямой ответ ML1 по текущей JSON Schema и останавливает свои процессы.
Без --rules-path он честно воспроизводит ошибку пустого рабочего каталога.
Для уже поднятого ML1 предусмотрен --existing-ml1. Результаты и логи остаются в
игнорируемом cache/. Закрытые тестовые видео этот сценарий не открывает.

На этом CPU сервис ML1 обрабатывает один запрос одновременно. Для обычного запуска
backend задайте `WORKERS=1` (сейчас по умолчанию 2), чтобы очередь находилась в backend,
а не получала 503 от занятого ML1. Транспортные проверки проводились с WORKERS=1.
