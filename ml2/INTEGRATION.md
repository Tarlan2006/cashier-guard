# Интеграция ML1 из папки ml2

Дата: 2026-10-17. Ветка: `ml2-service`. Push не выполнялся.

## Границы изменений

Новый сервис находится в `ml2/`, порт **8001**, переменная **ML1_URL**.
Matching другого участника остаётся на **8002**, переменная **ML2_URL**.
`contracts/`, `backend/app`, `frontend`, `ml1/`, `data/rules.json` не изменены.
Кроме `ml2/` изменены только корневые README и .gitignore.

ML работает на Python 3.12.10; интеграционный backend запущен на Python 3.14.7.
Это разные виртуальные окружения. Модели находятся снаружи клона и подключены
через `ML_MODELS_DIR`; веса, данные, кэши и окружения в коммит не входят.

## Контракт и ошибки

`POST /analyze`, multipart `file` → analyze_video → ML1 Observation:

| Внутренний Event | ML1-контракт |
|---|---|
| rule_id + порядковый индекс + начало | id = rule_id:индекс:секунды |
| timecode_sec / first_seen | start_sec |
| max(first_seen, confirmed_at) | end_sec |
| description | description |
| 1–3 JPEG + фактические времена кадров | evidence_frames |

У ML1 Observation нет отдельных полей type/rule_id/confidence. Backend отбрасывает
посторонние поля при разборе Pydantic, поэтому добавление их в JSON не решит передачу
типов. Для текущих проверок rule_id находится в id. Нужен согласованный mapping
наблюдений в утверждённые rule_id участника 4, прежде чем включать matching.

Нулевое число срабатываний возвращает строго `{"schema_version":"1.0","events":[]}`.
Неизвестное/отключённое правило не публикуется. Ошибки не превращаются в пустой 200:
400 пустой файл, 408 таймаут загрузки, 413 размер, 415 формат, 422 декодирование,
503 занятость, 504 бюджет inference, 500 прочая ошибка. Ответов со статусом failed
наш сервис не создаёт. При аварии рабочего процесса `/health` становится 503;
для восстановления нужен перезапуск сервиса.

При пустом whitelist восприятие может полностью завершиться, но проверка правил
остаётся **partial**. Это передаётся заголовками `X-Analysis-Status: partial`,
`X-Analysis-Complete: false`, `X-Perception-Complete: true`, `X-Enabled-Rule-Count: 0`.
Во время транспортного теста ниже backend эти заголовки ещё не учитывал.
Текущая интеграция отклоняет такой ответ с `ML1_INCOMPLETE`, завершает задачу
ошибкой и исключает её из успешных проверок аналитики. Успешный транспортный тест
ниже **не подтверждает отсутствие нарушений**.

В существующем backend статусы ошибок уже называются `failed` в модели JobResponse.
Это расходится с новым требованием не возвращать failed; изменить их без изменения
защищённых backend/contracts/frontend нельзя. Предложение для участника 3: согласовать
состояние ошибки/неполноты и HTTP-поведение, сохраняя ошибку явно видимой.

## Проверка цепочки

Запущены реальный ML1 8001, реальный backend с PIPELINE_MODE=live 8000 и явно
тестовая заглушка `/match` 8002. Использованы только открытые видео 2 и 14.
API-ключ случайный, только в окружении процессов; в файлы и вывод не записан.
JPEG не выводились и не передавались внешним сервисам.

Первый запуск с исходным `data/rules.json` остановился с `RULES_EMPTY`:
видео 2 — 0,78 с, видео 14 — 0,40 с (полный HTTP/poll цикл). До ML1 backend не дошёл.
Это реальная ошибка конфигурации, а не результат «нарушений нет».

В `ml1/outputs/forte_rules_kz.json` уже есть 8 исследовательских правил команды
с источниками. `scripts/prepare_transport_catalog.py` структурно преобразует их
в **игнорируемую** копию `cache/integration/transport_catalog.json`; исходные
файлы не меняются. Сохраняются источник, пункт, условия применимости и исключения.
Отсутствующие реквизиты отвергаются, нормативные ссылки не придумываются.
В копии явно указано `integration_test_only=true`. Применимость каталога и его
публикация в data/rules.json требуют содержательной проверки участником 4.

Повторный транспортный прогон использует RULES_PATH на эту копию, а не подменяет
рабочий каталог. Заглушка matching возвращает no_violation для пустых наблюдений;
для непустых требует известный rule_id из переданного каталога. Она не проверяет
нормы, не заменяет сервис участника 2 и не включена в обычный запуск.

| Видео | Прямой ML1, с | Полная цепочка HTTP/poll, с | ML1 внутри backend, с | Итог |
|---|---:|---:|---:|---|
| 2 | 15.46 | 15.49 | 15.25 | done / no_violation |
| 14 | 49.18 | 50.34 | 50.02 | done / no_violation |

Это тест транспорта с заглушкой matching и пустым whitelist правил. Оба ответа ML1 проверены по текущей JSON Schema; истинность вердикта по видео не проверяется. Модели загружены по одному разу; кэш признаков сбрасывается между запросами, что отражено заголовком X-Input-Cache. Повреждённый MOV вернул HTTP 422, а не пустой успешный ответ. Логи и исходные JSON находятся только в игнорируемом cache/integration_final/.


## Таймауты участнику 3

В `backend/app/pipeline.py` сейчас ML1/ML2 используют read=90 с и общий предел
HTTP-запроса 120 с. Свежий тест 285-секундного видео в исходном проекте занял
103,84 с: он уже превышает read=90 с на **13,84 с**. Максимальный бюджет ML1 — 170 с.

Для поддержки всего бюджета ML1 предлагается отдельно для его стадии:

| Лимит | Сейчас | Предложение | Изменение |
|---|---:|---:|---:|
| ML1 read | 90 с | 180 с | +90 с |
| ML1 полный HTTP-запрос | 120 с | 190 с | +70 с |
| ML2 read / полный запрос | 90 / 120 с | отдельно согласовать, например 30 / 35 с | не растягивать оба этапа автоматически |

JOB_TIMEOUT_SECONDS по умолчанию 290 с уже больше ML1-бюджета. При потолке загрузки
60 с, ML1=190 с и ML2=35 с остаётся около 5 с на очередь/подготовку; общий дедлайн
по-прежнему обязателен. Для большой очереди бюджет нужно распределять по оставшемуся
времени, а не обещать независимые максимумы всех стадий. Жёсткий backend-потолок
295 с в этом изменении не тронут. На видео 2/14 отдельные текущие измерения могут
укладываться в 90 с; это не покрывает весь заявленный диапазон входных видео.

## Воспроизведение проверки

Из ml2, при доступных локальных FFmpeg/FFprobe и уже установленном backend:

```powershell
.venv/Scripts/python.exe scripts/prepare_transport_catalog.py
.venv/Scripts/python.exe scripts/integration_check.py --open-root C:/path/to/data/open --ffmpeg-bin C:/path/to/ffmpeg/bin --models C:/path/to/models --rules-path cache/integration/transport_catalog.json
```

Скрипт поднимает тестовые процессы, вызывает POST /api/v1/analyze, опрашивает job,
проверяет прямой ответ ML1 по текущей JSON Schema и останавливает свои процессы.
Без --rules-path он честно воспроизводит ошибку пустого рабочего каталога.
Для уже поднятого ML1 предусмотрен --existing-ml1. Результаты и логи остаются в
игнорируемом cache/. Закрытые тестовые видео этот сценарий не открывает.

На этом CPU сервис ML1 обрабатывает один запрос одновременно. Для обычного запуска
backend задайте `WORKERS=1` (сейчас по умолчанию 2), чтобы очередь находилась в backend,
а не получала 503 от занятого ML1. Транспортные проверки проводились с WORKERS=1.
