# ml2 — локальный анализ видео кассира (сервис ML1-контракта)

Папка называется `ml2/`, но сервис реализует контракт ML1: порт 8001, `POST /analyze`
(`ML1_URL` в backend). Материалы участника 2 в `ml1/` не затронуты. Каталог
нормативных правил, matching и окончательный `rule_id` — сервис на порту 8002
другого участника. Внутренние идентификаторы кандидатов ML1 требуют согласованного
mapping в этот каталог; см. [INTEGRATION.md](INTEGRATION.md).
`ml1/` — материалы участника 2; экспериментальный [PR #4](https://github.com/Tarlan2006/cashier-guard/pull/4)
остаётся draft и не входит в данный HTTP-сервис.

## Что делает

По видео сверху кассовой зоны сервис находит людей, строит треки, определяет роли
кандидатов в кассиры и клиенты, ищет опорные предметы — счётную машинку и сейф —
и строит хронологию. Всё локально, на CPU, без облачных AI API.

## Текущий статус (честно)

- Кандидат в кассиры найден в 39/40 открытых видео, машинка — в 39/40, сейф —
  в 25/40. Это наличие кандидатов, а не точность распознавания.
- Наличие **или отсутствие** клиента совпало с ручной проверкой в 13/13 случаях:
  8 с клиентом и 5 без клиента. Это не 13 обнаруженных клиентов и не проверка
  правильности каждого назначенного трека.
- **Правила нарушений пока не включены**: ни одно не прошло критерий TP ≥ 3,
  FP ≤ 1 на нормальных видео. Классификатор состояния стола на leave-one-video-out
  дал 25,9% при базовом 55,6%; использовались слабые метки эпизодов.
- После успешного perception API возвращает `{"schema_version":"1.0","events":[]}`:
  «наблюдений нет» в ответе контракта; сейчас включённых правил нет. Это HTTP 200 с заголовком
  `X-Rules-Enabled: none`, без заголовков partial/incomplete. Backend принимает
  пустой список. В проверенной цепочке matching stub возвращает `no_violation`,
  backend сохраняет этот вердикт; ML1 собственного verdict не выдаёт.
  Отсутствие нарушений этим не подтверждено.
- Детали — деньги на столе, открытый сейф, предметы в руках — требуют точных меток
  состояний и/или более сильной модели сцены. Агрегированные отчёты:
  [docs/](docs/), [eval/v6/report.md](eval/v6/report.md).
  Исходные метки, таблицы по отдельным видео и кадры не входят в Git.

## Известные ограничения

- Выключенные правила оставляют events пустым; качество поиска нарушений этим не измеряется.
- Наличие кандидата в кассиры или якоря не равно подтверждённой точности его определения.
- Отражения, перекрытия и другой ракурс могут нарушать треки и поиск опорных предметов.
- Деньги/предметы на столе, открытый сейф и блокировка ноутбука надёжно не распознаются.
- Геометрия сцены приблизительная; калиброванной плоскости пола нет.
- Время CPU-прогонов меняется; при увеличении шага короткие события могут пропускаться.
- HTTP API не отдаёт факты ролей/якорей; успешный ответ на вариацию не доказывает их устойчивость.

Исторические измерения: [eval/results.md](eval/results.md). Аудиты:
[сеть](eval/network_audit.md), [HTTP-устойчивость](eval/robustness/report.md),
[лицензии и состав Git](../THIRD_PARTY_LICENSES.md). Пороги и модельная логика не менялись.

## Конвейер

Видео → кадры каждые 0,5 с → RT-DETR R18 (ONNX Runtime) → треки и фильтр отражений
→ якоря (SigLIP) → роли → хронология → включённые правила → события с 1–3 JPEG.

Кадры декодируются локальным PyAV 19.0.1. Время кадра — `frame.pts * frame.time_base`,
а не номер кадра / FPS. Время не сдвигается к нулю: сохраняются VFR-интервалы и
начальная задержка видеодорожки. В период до первого кадра факты не создаются.
FPS и число кадров используются только как справочные метаданные.
Преобразование YUV → BGR явно сохраняет BT.601 прежнего OpenCV-конвейера,
чтобы смена декодера не меняла входные пиксели моделей и гистограммы одежды.
Это режим совместимости прежней обработки, а не автоматический выбор матрицы
по цветовым тегам видео. Декодирование использует один поток, чтобы снизить конкуренцию
с потоками детектора и энкодера сцены;
шаг фактов остаётся 0,5 с до срабатывания общего бюджета времени.

Модели загружаются один раз при старте рабочего процесса, признаки кропов очищаются
между видео. CPU обрабатывает один запрос одновременно; занятость возвращает 503.
При аварии рабочего процесса нужен перезапуск сервиса.

## API

- `POST /analyze`, multipart `file`, MOV/MP4 →
  [contracts/ml1-response.schema.json](../contracts/ml1-response.schema.json).
  Принимается нормализованный backend файл `video.mp4`: H.264, yuv420p,
  без звука, MIME `video/mp4`.
- `GET /health` — готовность моделей и список включённых правил.
- Ошибки — HTTP-статусом: 422 для повреждённого видео, 504 при превышении бюджета
  inference. Ошибки не маскируются пустым успешным ответом.
  Только при прерванном по таймауту анализе HTTP 504 содержит
  `X-Analysis-Status: partial` и `X-Analysis-Complete: false`.

В ML1-контракте нет отдельных полей type/rule_id/confidence: внутренний идентификатор
кандидата находится в Observation.id. Evidence уменьшаются до стороны 1280 с проверкой
лимитов 8 млн пикселей и 4 млн символов base64 на JPEG.
Текущий backend отклоняет заголовки неполноты; поэтому отсутствие включённых
правил ими не помечается. Подробности: [INTEGRATION.md](INTEGRATION.md).

## Запуск

Из папки `ml2/`, отдельное окружение Python 3.12:

```powershell
py -3.12 -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe scripts/download_models.py --download
.venv/Scripts/python.exe -m uvicorn service.app:app --host 127.0.0.1 --port 8001 --workers 1
```

Загрузчику обязателен режим `--download` или `--source` с путём к готовому комплекту.
Проверка существующего комплекта без копирования и сети:
`python scripts/download_models.py --source models --verify-only`.
Веса не в Git; revision и SHA-256 — [configs/model_manifest.json](configs/model_manifest.json).
Скачивание запускается только явно при подготовке; inference работает без сети.
Проверка существующего комплекта испытана; повторный сетевой download/export
в интеграционной сессии не запускался.

Веса снаружи репозитория можно подключить через `ML_MODELS_DIR` — родительскую папку
`rtdetr_r18vd/` и `siglip-base-patch16-224/`. Конфиг: `configs/perception.json`,
альтернативный путь — `PERCEPTION_CONFIG`. Для backend на этом CPU рекомендуется `WORKERS=1`.

## Перенос на другую машину (macOS arm64)

Для Apple M2 используйте нативный **Python 3.12 arm64**, macOS 14 или новее
и Git. Создайте отдельное окружение; команды выполняются из `cashier-guard/ml2`:

```bash
uname -m  # arm64
python3.12 -m venv .venv
source .venv/bin/activate
python -c 'import platform; print(platform.machine())'  # arm64
python -m pip install -r requirements.txt
python -m pip check
```

Веса не входят в Git. Выберите **один** способ подготовки:

1. Скачать закреплённые исходные веса и экспортировать ONNX локально:
   `python scripts/download_models.py --download`.
2. Перенести готовый `ml2-weights.zip` (только runtime-веса, признаки и manifest),
   сравнить SHA-256 с хешем отправителя и распаковать:

   ```bash
   shasum -a 256 /path/to/ml2-weights.zip
   mkdir -p models
   unzip /path/to/ml2-weights.zip -d models
   python scripts/download_models.py --source models --verify-only
   ```

Внутри `models/` должны оказаться `installation_manifest.json`,
`rtdetr_r18vd/` и `siglip-base-patch16-224/`. Последняя команда проверяет все
runtime-файлы без сети; depth-модель для запуска не нужна. Сетевой экспорт
на самом Mac не проверен; готовый архив позволяет обойти этот этап.

Запустите сервис на CPU с одним worker; во втором терминале проверьте готовность:

```bash
python -m uvicorn service.app:app --host 127.0.0.1 --port 8001 --workers 1
# Во втором терминале, после загрузки моделей:
curl --fail http://127.0.0.1:8001/health
```

Backend должен работать с `PIPELINE_MODE=live` и `ML1_URL=http://127.0.0.1:8001`.
Наличие колёс не заменяет проверку запуска и времени обработки на самом Mac.

## Локальная проверка цепочки

`scripts/matching_stub.py` — **тестовая заглушка** сервиса другого участника на
8002. Она проверяет контракт и копирует `rule_id`, уже записанный адаптером ML1
в `id` наблюдения (`rule_id:index:seconds`); смысл видео и применимость нормы
не проверяет. Пустые наблюдения дают `no_violation`, неизвестный ID или
повреждённый запрос — HTTP 422. Ответ помечен `X-Matching-Stub: true`.
Это отдельный тестовый процесс; обычный сервис анализа его не запускает.

Из `ml2/`, с активным окружением Python 3.12 и установленным backend:

```powershell
# Только структурная копия существующего исследовательского каталога команды:
python scripts/prepare_transport_catalog.py
python scripts/run_chain.py --open-root DATA_OPEN --models MODEL_ROOT --ffmpeg-bin FFMPEG_BIN --rules-path cache/integration/transport_catalog.json --videos 2 14 --expect-empty
# Та же команда через scripts/run_chain.ps1, либо python -m scripts.run_chain.
```

`DATA_OPEN` — путь к разрешённому `data/open`, `MODEL_ROOT` — комплект RT-DETR/SigLIP.
По умолчанию используются порты 8000/8001/8002, `WORKERS=1`, `PIPELINE_MODE=live`.
Скрипт проверяет занятость портов, генерирует ключ только в памяти/окружении,
запускает сервисы, загружает видео в backend, опрашивает job и проверяет JSON/JPEG.
Останавливает только свои процессы, включая дочерний процесс моделей.
`--existing-ml1` сохраняет уже работающий ML1; `--direct-ml1` дополнительно проверяет
прямой POST к ML1 перед каждым полным запросом. Альтернативный Python backend:
`--backend-python PYTHON`; отдельная тестовая копия: `--backend-dir BACKEND_DIR`.

Ответы с кадрами, логи и отчёт остаются в игнорируемом `cache/chain/`;
`--output-dir` допускает только новую папку внутри `ml2/cache/`. Ключ и base64
в консоль не выводятся. Код выхода 0 означает, что все проверки прошли;
некорректный ответ, failed job или таймаут дают ненулевой код, без подмены вердикта.
`--expect-empty` проверяет режим отключённых правил, а не качество распознавания.

Отдельная проверка сохранённого ответа:

```powershell
python scripts/check_events.py cache/chain/RUN/02.ml1.json --kind ml1 --expect-empty
python scripts/check_events.py cache/chain/RUN/02.job.json --kind job --rules-path cache/integration/transport_catalog.json --expect-empty
```

Файл `.ml1.json` создаётся только с `--direct-ml1`. Валидатор проверяет схемы из
`contracts/`, интервалы, границы времени, уникальность ID наблюдений, согласованность
вердикта, каталог и декодируемость 1–3 JPEG (≤8 млн пикселей, ≤4 млн символов base64).
Повреждённые кадры, failed/processing и отсутствующее поле событий не считаются успехом.
Для ML1 без длительности используйте `--duration SECONDS`, чтобы проверить верхнюю
границу времени; у job длительность берётся из самого ответа.

**Историческое ограничение backend на Windows:** до `20d3f21` нормализация
блокировалась на Unix-only `signal.SIGXFSZ` и `resource.RLIMIT_FSIZE`.
Исправление уже в main; актуальные backend-тесты на Windows — 217 passed.
Launcher пока сохраняет прежний Windows-маршрут через Docker/Linux backend.
Исторические замеры: [eval/chain/report.md](eval/chain/report.md).

Патч [patches/backend-ml-timeouts.patch](patches/backend-ml-timeouts.patch)
**уже применён в main (`8cf0d4c`)**: ML1 read=180 с / total=190 с,
ML2 read=90 с / total=100 с. Общий дедлайн job не менялся: по умолчанию 290 с,
допустимый предел 295 с. Файл патча оставлен для истории и обратной проверки;
повторно применять его к main не нужно. Проверка из корня репозитория
(ничего не отменяет и не редактирует):

```powershell
git apply --reverse --check ml2/patches/backend-ml-timeouts.patch
```

Launcher и Docker build-скрипт проверяют прямую и обратную применимость:
старый backend патчится только в cache/image, готовый используется без повторного
применения с сообщением `timeouts already applied`; несовместимое состояние — ошибка.

Запуск трёх сервисов одной командой на Linux или Windows с Docker-backend:
[RUNBOOK.md](eval/chain/RUNBOOK.md), `scripts/launch_chain.py`.
На этом компьютере WSL не установлен, Docker не найден; контейнерный запуск
не проверен. Native backend на Windows запускать через launcher нельзя:
он останавливается с объяснением до загрузки моделей, без обхода квот.

на диагональ кадра. В `backend/pipeline/perception/distances.py` доступны только
для явного эксперимента нижняя точка рамки, гомография автоматического
четырёхугольника стола/якорей (A) и относительная глубина (B).
Автоматический четырёхугольник не считается калибровкой пола: якоря находятся
на разных высотах, стопы бывают закрыты столом. Относительная глубина также
не даёт метрических расстояний без калибровки камеры. Решение о включении
и результаты: [eval/v8/report.md](eval/v8/report.md).

Опциональная модель B: **Depth Anything V2 Small**, официальный
[`depth-anything/Depth-Anything-V2-Small-hf`](https://huggingface.co/depth-anything/Depth-Anything-V2-Small-hf),
24,8 млн параметров, revision `5426e4f0f36572d16453bbda7a8389317b1bef99`.
На странице этой модели подтверждена **Apache-2.0**; исходная
[Small-модель](https://huggingface.co/depth-anything/Depth-Anything-V2-Small)
также Apache-2.0. Base/Large с другой лицензией не используются.
SHA-256 и размеры всех файлов закреплены в `configs/depth_model_manifest.json`.
Новых зависимостей нет: используются уже закреплённые Torch и Transformers.

```powershell
# Однократная явная подготовка только опциональной Small-модели:
python scripts/download_models.py --depth-small
python scripts/download_models.py --depth-small --verify-only
# Копирование готового проверенного комплекта вместо скачивания:
python scripts/download_models.py --depth-small --depth-source MODEL_ROOT
```

Эти команды не заменяют комплект RT-DETR/SigLIP. При запуске обычного сервиса
depth-модель не загружается. Эксперимент использует локальные файлы,
`local_files_only=True`, отключённую сеть Hugging Face и один вызов depth-модели
на временную медиану девяти кадров каждого видео. Конфигурация устройства
передаётся явно; результаты CPU измеряются отдельно от загрузки модели.

## Структура

`service/` — FastAPI; `backend/pipeline/perception/` — восприятие;
`backend/pipeline/` — оркестрация, кандидаты правил и бюджет;
`scripts/` — подготовка весов и отладка; `tests/`, `docs/`, `eval/`.
Matching-заглушка в scripts предназначена только для теста транспорта.

**Legacy — не удалять до сдачи:**

| Модуль | Статус |
|---|---|
| `backend/pipeline/perception/roles.py` | Прежние роли; RoleAssigner ещё используется в первичном проходе |
| `backend/pipeline/perception/anchors.py` | Якоря ветки v4; текущая ветка использует anchors_v2.py |
| `backend/pipeline/perception/refine.py` | Совместимость с v4 и действующая маршрутизация в refine_v5.py |
| `backend/pipeline/state_engine.py` | Прежний движок v4; v6 использует track_rules.py и semantic_engine.py |
| `backend/pipeline/perception/torch_detector.py` | Альтернативный PyTorch-детектор; CPU по умолчанию использует ONNX |

Legacy не означает отсутствие вызовов: часть кода остаётся инфраструктурой
совместимости. Модули в этой правке не удалялись и не рефакторились.

## Контракт итоговой оценки backend

Текущий backend сохраняет `assessment` (`strong_evidence` / `needs_review`) и
`assessment_reason` от отдельного matching-сервиса на 8002. Это не поля ответа
данного ML1-сервиса. Полные требования к оценке, проверенному `rule_id`, кадрам и
совместимости прежних результатов находятся в [contracts/README.md](../contracts/README.md).
Ошибка модели или таймаут остаются HTTP-ошибкой. Отсутствие включённых правил
является успешным ответом без наблюдений. В проверенной цепочке matching stub
возвращает `no_violation`, который сохраняет backend; ML1 не выдаёт verdict.
