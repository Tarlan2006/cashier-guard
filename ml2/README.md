# ml2 — локальный анализ видео кассира (сервис ML1-контракта)

Папка называется `ml2/`, но сервис реализует контракт ML1: порт 8001, `POST /analyze`
(`ML1_URL` в backend). Материалы участника 2 в `ml1/` не затронуты. Каталог
нормативных правил, matching и окончательный `rule_id` — сервис на порту 8002
другого участника. Внутренние идентификаторы кандидатов ML1 требуют согласованного
mapping в этот каталог; см. [INTEGRATION.md](INTEGRATION.md).

## Что делает

По видео сверху кассовой зоны сервис находит людей, строит треки, определяет роли
кандидатов в кассиры и клиенты, ищет опорные предметы — счётную машинку и сейф —
и строит хронологию. Всё локально, на CPU, без облачных AI API.

## Текущий статус (честно)

- Кандидат в кассиры найден в 39/40 открытых видео, машинка — в 39/40, сейф —
  в 25/40. Это наличие кандидатов, а не точность распознавания.
- Наличие **или отсутствие** клиента совпало с ручной проверкой в 13/13 случаях:
  8 с клиентом и 5 без клиента. Это не 13 обнаруженных клиентов и не проверка
  правильности каждого назначенного трека.
- **Правила нарушений пока не включены**: ни одно не прошло критерий TP ≥ 3,
  FP ≤ 1 на нормальных видео. Классификатор состояния стола на leave-one-video-out
  дал 25,9% при базовом 55,6%; использовались слабые метки эпизодов.
- После успешного perception API возвращает `{"schema_version":"1.0","events":[]}`:
  включённых правил сейчас нет. Это обычный HTTP 200 с информационным заголовком
  `X-Rules-Enabled: none`, без заголовков partial/incomplete. Backend принимает
  пустой список и трактует его как `no_violation`; это не подтверждение отсутствия
  нарушений, а результат работы с пустым списком включённых правил.
- Детали — деньги на столе, открытый сейф, предметы в руках — требуют точных меток
  состояний и/или более сильной модели сцены. Агрегированные отчёты:
  [docs/](docs/), [eval/v6/report.md](eval/v6/report.md).
  Исходные метки, таблицы по отдельным видео и кадры не входят в Git.

## Конвейер

Видео → кадры каждые 0,5 с → RT-DETR R18 (ONNX Runtime) → треки и фильтр отражений
→ якоря (SigLIP) → роли → хронология → включённые правила → события с 1–3 JPEG.

Кадры декодируются локальным PyAV 19.0.1. Время кадра — `frame.pts * frame.time_base`,
а не номер кадра / FPS. Время не сдвигается к нулю: сохраняются VFR-интервалы и
начальная задержка видеодорожки. В период до первого кадра факты не создаются.
FPS и число кадров используются только как справочные метаданные.

Модели загружаются один раз при старте рабочего процесса, признаки кропов очищаются
между видео. CPU обрабатывает один запрос одновременно; занятость возвращает 503.
При аварии рабочего процесса нужен перезапуск сервиса.

## API

- `POST /analyze`, multipart `file`, MOV/MP4 →
  [contracts/ml1-response.schema.json](../contracts/ml1-response.schema.json).
  Принимается нормализованный backend файл `video.mp4`: H.264, yuv420p,
  без звука, MIME `video/mp4`.
- `GET /health` — готовность моделей и список включённых правил.
- Ошибки — HTTP-статусом: 422 для повреждённого видео, 504 при превышении бюджета
  inference. Ошибки не маскируются пустым успешным ответом.
  Только при прерванном по таймауту анализе HTTP 504 содержит
  `X-Analysis-Status: partial` и `X-Analysis-Complete: false`.

В ML1-контракте нет отдельных полей type/rule_id/confidence: внутренний идентификатор
кандидата находится в Observation.id. Evidence уменьшаются до стороны 1280 с проверкой
лимитов 8 млн пикселей и 4 млн символов base64 на JPEG.
Текущий backend отклоняет заголовки неполноты; поэтому отсутствие включённых
правил ими не помечается. Подробности: [INTEGRATION.md](INTEGRATION.md).

## Время и ресурсы (i5-1240P, CPU)

Видео 14 — около 50 с; склеенное видео длительностью около 285 с — около 104 с.
Это исторические замеры v6 до замены декодера на PyAV; скорость после замены
на реальных видео в этой правке не измерялась. Длинное видео проверено без кэша.
Объём и пиковое потребление RAM в этих замерах
не фиксировались, поэтому утверждение о работе в пределах 8 ГБ не подтверждено.

Адаптация шага после 150 с **обработки**: с 0,5 до 2–10 с; мягкая остановка 168 с,
внешний предел 170 с. При увеличенном шаге короткие события могут быть пропущены.
Рекомендуемые таймауты backend: ML1 read 180 с, полный запрос 190 с;
см. [INTEGRATION.md](INTEGRATION.md).

## Запуск

Из папки `ml2/`, отдельное окружение Python 3.12:

```powershell
py -3.12 -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe scripts/download_models.py --download
.venv/Scripts/python.exe -m uvicorn service.app:app --host 127.0.0.1 --port 8001 --workers 1
```

Загрузчику обязателен режим `--download` или `--source` с путём к готовому комплекту.
Проверка существующего комплекта без копирования и сети:
`python scripts/download_models.py --source models --verify-only`.
Веса не в Git; revision и SHA-256 — [configs/model_manifest.json](configs/model_manifest.json).
Скачивание запускается только явно при подготовке; inference работает без сети.
Проверка существующего комплекта испытана; повторный сетевой download/export
в интеграционной сессии не запускался.

Веса снаружи репозитория можно подключить через `ML_MODELS_DIR` — родительскую папку
`rtdetr_r18vd/` и `siglip-base-patch16-224/`. Конфиг: `configs/perception.json`,
альтернативный путь — `PERCEPTION_CONFIG`. Для backend на этом CPU рекомендуется `WORKERS=1`.

Тесты на синтетических данных, без исходных видео и весов (проверенный набор — 141):

```powershell
.venv/Scripts/python.exe -m unittest discover -s tests
```

`pytest` не входит в requirements.txt; команда выше соответствует проверенному запуску.

## Структура

`service/` — FastAPI; `backend/pipeline/perception/` — восприятие;
`backend/pipeline/` — оркестрация, кандидаты правил и бюджет;
`scripts/` — подготовка весов и отладка; `tests/`, `docs/`, `eval/`.
Matching-заглушка в scripts предназначена только для теста транспорта.

**Legacy — не удалять до сдачи:**

| Модуль | Статус |
|---|---|
| `backend/pipeline/perception/roles.py` | Прежние роли; RoleAssigner ещё используется в первичном проходе |
| `backend/pipeline/perception/anchors.py` | Якоря ветки v4; текущая ветка использует anchors_v2.py |
| `backend/pipeline/perception/refine.py` | Совместимость с v4 и действующая маршрутизация в refine_v5.py |
| `backend/pipeline/state_engine.py` | Прежний движок v4; v6 использует track_rules.py и semantic_engine.py |
| `backend/pipeline/perception/torch_detector.py` | Альтернативный PyTorch-детектор; CPU по умолчанию использует ONNX |

Legacy не означает отсутствие вызовов: часть кода остаётся инфраструктурой
совместимости. Модули в этой правке не удалялись и не рефакторились.

## Контракт итоговой оценки backend

Текущий backend сохраняет `assessment` (`strong_evidence` / `needs_review`) и
`assessment_reason` от отдельного matching-сервиса на 8002. Это не поля ответа
данного ML1-сервиса. Полные требования к оценке, проверенному `rule_id`, кадрам и
совместимости прежних результатов находятся в [contracts/README.md](../contracts/README.md).
Ошибка модели или таймаут остаются HTTP-ошибкой. Отсутствие включённых правил
является успешным пустым результатом, который backend трактует как `no_violation`.
