# Cashier Guard

Сервис для кейса ForteBank: загрузка видео, обработка в очереди, API и просмотр событий
с точными таймкодами, кадрами и источниками правил. **Сейчас используется явно обозначенный
деморежим: события задаются сценарием, распознавание нарушений ещё не подтверждено.**

Рабочий проект — `cashier-guard`. Соседние репозитории не нужны для запуска.

## Команда и папки

| Папка | Ответственный | Что передать для интеграции |
|---|---|---|
| `ml1/` | Материалы участника 2 | Переданные материалы команды; этой интеграцией не изменены. Каталог нормативов и matching — отдельный сервис на 8002 (`ML2_URL`) |
| `ml2/` | Наш AI/CV | Локальный анализ видео кассира: люди, треки, отражения, якоря, роли и хронология; ML1-контракт, порт 8001 (`ML1_URL`), Python 3.12. Правила нарушений пока выключены |
| `frontend/`, `backend/` | Frontend + Backend | Пользовательский сценарий, API, хранение текущей задачи, обработка ошибок и развёртывание |
| `data/` | Данные, нормативы, качество | Проверенный каталог правил, размеченные видео и отдельная проверочная выборка |
| `contracts/` | Согласуют все | Версии и JSON-схемы обмена; изменение схемы согласуется до push модели |

## Локальный запуск

Наш сервис анализа находится в `ml2/` и обслуживает **ML1** на порту **8001**.
Он использует отдельное окружение Python 3.12; backend сохраняет своё окружение
Python 3.14. Папка `ml1/` сохранена. Matching на 8002 остаётся отдельным сервисом ML2.
Установка: [ml2/README.md](ml2/README.md), ограничения: [ml2/INTEGRATION.md](ml2/INTEGRATION.md).
В v6 разрешённых правил пока нет: perception работает, но HTTP-заголовки указывают
`partial`; пустой `events` не подтверждает отсутствие нарушений.

Нужны Node.js 22.12+ либо 24+, Python 3.14.0, `uv` и FFmpeg с кодировщиком `libx264`
(`ffmpeg`, `ffprobe` в PATH).
Docker использует Node.js 24.13.0, Python 3.14.0 и uv 0.12.18. Зависимости приложения
фиксируются `frontend/package-lock.json` и `backend/uv.lock`; установка не обновляет lock-файлы.
Если Python 3.14.0 отсутствует, `uv` может загрузить его при setup. Первичная установка
зависимостей/образов/весов требует сети; сама обработка использует только локальные ML-сервисы.

Из корня проекта:

```bash
./scripts/setup.sh
./scripts/demo_video.sh
./scripts/dev.sh
```

- Сайт: <http://127.0.0.1:5173>.
- API: <http://127.0.0.1:8000/docs>.
- Видео для проверки: `work/demo/SYNTHETIC_cashier_guard_demo_12_seconds.mov`.
- Setup создаёт случайный `API_KEY` в корневом `.env` с правами `0600`, без вывода значения.
  Откройте `.env` в своём редакторе и введите ключ в поле сайта. Существующий ключ сохраняется;
  пустой/шаблонный ключ заменяется, остальные настройки остаются прежними.
- `dev.sh` использует фиксированные порты **8000/5173**, соответствующие прокси Vite.
  При занятом порте скрипт завершится с ошибкой. `PORT` применяется только к Docker Compose.
- Ctrl+C останавливает оба процесса. После изменения серверной конфигурации перезапустите их.

Для единого адреса без Vite:

```bash
(cd frontend && npm run build)
(cd backend && uv run --frozen uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1 --no-access-log)
```

Сайт и API будут на <http://127.0.0.1:8000>. Соберите frontend до запуска backend.

## Поведение проверок и хранение

`POST /api/v1/analyze` принимает multipart-поле `file`; `GET /api/v1/jobs/{job_id}`
возвращает статус. Оба требуют заголовок `X-API-Key`. Сохраняются статусы
`processing` / `done` / `failed`, вердикты `violation` / `no_violation` и обязательные
поля события `type`, `timecode_sec`, `description`, `evidence_frames` (1–3 JPEG в base64).
Ошибка, недоступность или некорректный ответ ML приводят к ошибке обработки, а не к `no_violation`.
Подробные форматы и ошибки — в `contracts/` и `/docs`.

Текущая задача сохраняется в `sessionStorage` этой вкладки, её статус и результат — в SQLite
`backend/storage/jobs.sqlite3` (в Docker — `/app/storage/jobs.sqlite3`). После обновления
страницы сайт запрашивает сохранённый `job_id`; это восстановление одной проверки,
не личный кабинет и не история всех загрузок. Ключ вводит пользователь; он не встроен в сборку.
Локальное видео и Object URL не сохраняются: чтобы снова смотреть исходник и переходить
по его шкале, после обновления нужно повторно выбрать исходный файл. Доказательства из
результата доступны без восстановления локального файла.

После перезапуска backend завершённые результаты сохраняются, а незавершённые задачи
получают `failed` с кодом `SERVER_RESTARTED` и предложением загрузить видео снова.
Автоматического повторного запуска ML после перезапуска нет. Исходные `.upload` и
преобразованные `.normalized.mp4` удаляются после завершения, ошибки или отмены;
оставшиеся прерванные загрузки и преобразования убираются при старте.
Завершённые записи с доказательствами живут **1 час с завершения**, затем удаляются
фоновым проходом с интервалом **60 секунд**. По истечении срока API возвращает 404.
Предел количества записей и диска дополнительно ограничивает накопление данных.

При ошибке записи SQLite задача получает `failed / STORAGE_WRITE_FAILED` без вердикта.
Если не удаётся сохранить даже эту ошибку, backend временно держит небольшой ответ
в памяти, блокирует новые загрузки и повторяет сохранение при фоновой очистке.
Удаление исходника и отмена обработки всё равно выполняются. При перезапуске до
восстановления БД незавершённая сохранённая запись получит `SERVER_RESTARTED`.

Запускайте **один процесс Uvicorn и один экземпляр backend на хранилище**.
`WORKERS=2` — число фоновых обработчиков внутри этого процесса, не `uvicorn --workers 2`.
SQLite и очередь в текущей реализации не предназначены для нескольких реплик.

## Конфигурация и бюджет времени

| Переменная | По умолчанию | Значение |
|---|---:|---|
| `API_KEY` | отсутствует | Обязательный секрет серверной конфигурации |
| `PIPELINE_MODE` | `demo` | `demo` или `live` |
| `MAX_UPLOAD_MB` | `100` | Лимит исходного файла в MiB; MOV, MP4, AVI, MKV, WEBM |
| `JOB_TIMEOUT_SECONDS` | `290` | Общий серверный бюджет, максимум 295 секунд |
| `UPLOAD_TIMEOUT_SECONDS` | `60` | Предел загрузки внутри общего бюджета |
| `WORKERS` / `QUEUE_SIZE` | `2` / `16` | Фоновые обработчики и очередь |
| `NORMALIZATION_WORKERS` | `1` | Максимум одновременных преобразований FFmpeg |
| `MAX_NORMALIZED_MB` | `512` | Максимальный размер одного подготовленного MP4 в MiB, дополнительно ограничен доступным диском |
| `MAX_CONCURRENT_UPLOADS` | `2` | Одновременные приёмы файлов |
| `MAX_STORAGE_MB` | `2048` | Ограничение занимаемого хранилища |
| `MAX_STORED_JOBS` | `128` | Ограничение числа сохранённых задач |
| `RESULT_TTL_HOURS` | `1` | Хранение завершённого результата |
| `CLEANUP_INTERVAL_SECONDS` | `60` | Период автоматической очистки |
| `STORAGE_DIR` | `backend/storage` | SQLite и временные файлы; в Docker переопределён |
| `RULES_PATH` | `data/rules.json` | Рабочий проверенный каталог; в Docker переопределён |
| `ML1_URL` / `ML2_URL` | `http://127.0.0.1:8001` / `http://127.0.0.1:8002` | Базовые адреса локальных сервисов |

При сохранённом старом `.env` его значения имеют приоритет: например, прежние `280` секунд
не заменяются автоматически на `290`. Увеличение таймаута сверх максимума запрещено.
Бюджет отсчитывается при поступлении загрузки в backend и включает приём тела, очередь,
проверку содержимого, преобразование FFmpeg и оба ML-этапа. Это ограничение времени, а не обещание успешного анализа любого
видео за пять минут. Задача, не уложившаяся в срок, завершается ошибкой. Поля измерения
этапов возвращаются с результатом. Время до первого запроса на медленном клиентском
соединении и качество реальных моделей нужно измерять отдельно на целевом сервере.
Не включайте буферизацию тела запроса на дополнительном прокси: иначе загрузка перед
backend окажется вне серверного измерения.

`GET /api/v1/health` проверяет доступность backend; `GET /api/v1/ready` отдельно сообщает
готовность FFmpeg, правил и ML-сервисов. ML проверяется только по TCP; ответ явно содержит
`processing_verified: false`, а ML-проверки — `check: "tcp"`, `model_verified: false`.
Это не подтверждает корректность модели, весов и ответа. В `demo` внешние модели и
рабочий каталог не требуются.

## Поддерживаемые видео и подготовка

Сайт принимает **MOV, MP4, AVI, MKV и WEBM** до установленного размера и 10 минут.
FFprobe проверяет фактический контейнер, наличие видеодорожки, кодек и длительность.
Переименование произвольного файла в `.mp4` не делает его допустимым видео.
Браузер может не воспроизводить AVI/MKV и отдельные кодеки MOV: это ограничение
локального предпросмотра, отправка файла на анализ остаётся доступной.

На этапе **«Подготовка и преобразование»** backend локально создаёт MP4: H.264,
`yuv420p`, одна видеодорожка, без аудио, субтитров и вложений. Этот файл используется
для ML1, демонстрационного анализа и извлечения JPEG. Сейчас выполняется полное
перекодирование, в том числе совместимых MP4; оптимизация через копирование потока
не применяется. FFmpeg не получает сетевых протоколов, списков воспроизведения или
доступа к внешним дорожкам MOV. Контейнер выбирается по содержимому файла.

Частота кадров не принудительно выравнивается: порядок и временные интервалы кадров
сохраняются, включая VFR. Повороты на 90°/180°/270° применяются к изображению;
разрешение не уменьшается. Нечётная сторона дополняется на один пиксель для `yuv420p`
без обрезки. Сохраняется соотношение сторон, включая sample aspect ratio.
Длительность и таймкоды сверяются по видеодорожке: хвост аудио после последнего
видеокадра не превращается в дополнительные кадры. Лимит 10 минут проверяется
по всему исходному контейнеру, включая аудио.
Необычный угол поворота или временная шкала, которую невозможно безопасно сохранить,
дают явную ошибку с просьбой повторно экспортировать запись.

Время отсчитывается от начала исходного контейнера. Абсолютное смещение начала
убирается, но задержка видеодорожки относительно начала ролика сохраняется: первый
кадр подготовленного MP4 может иметь PTS больше нуля. ML1 должен использовать PTS,
не вычитать время первого кадра и не предполагать постоянный FPS. `duration_sec`
включает начальный промежуток без изображения. Демо выбирает события внутри участка
с видеокадрами; в пустом промежутке доказательства не создаются.
Для исходников с ненулевым техническим началом задачи также содержат необязательное
`source_time_offset_sec`: сайт учитывает его при переходе к событию в локальном плеере.
Если браузер показывает шкалу, которую нельзя сопоставить с результатом, переходы
к событиям отключаются с пояснением; обычный просмотр и кадры результата доступны.

Ожидание свободного преобразователя и само преобразование входят в общий бюджет
`JOB_TIMEOUT_SECONDS`. На отмене/таймауте FFmpeg останавливается и ожидается завершение
процесса, затем удаляются обе временные копии. Для выходного файла резервируется место
с учётом `MAX_STORAGE_MB`, свободного диска, других преобразований и служебного запаса
SQLite. `MAX_NORMALIZED_MB` дополнительно ограничивается доступным остатком;
ограничение размера файла на уровне ОС не позволяет FFmpeg превысить выделенный предел.
Multipart-загрузки также резервируют место до записи временных файлов; при нехватке
свободного диска запрос завершается ошибкой 503 и освобождает резерв.
Поддерживаемое серверное окружение этой реализации — macOS/Linux.

После FFmpeg выход снова проверяется: контейнер, кодек, пиксельный формат, отсутствие
аудио, размеры, ориентация и длительность. Частичный или повреждённый результат не
передаётся ML1. Ошибки подготовки завершают задачу с `failed`, без вердикта.
Параметры времени и синхронизации описаны в [документации FFmpeg](https://ffmpeg.org/ffmpeg.html),
ограничение входных протоколов — в [документации протоколов](https://ffmpeg.org/ffmpeg-protocols.html),
внешние дорожки MOV — в [описании демультиплексора](https://ffmpeg.org/ffmpeg-formats.html#mov_002fmp4_002f3gp).

## Демонстрация без моделей

Результат теперь различает три уровня: красный **«Явные признаки нарушения»**,
жёлтый **«Требует уточнения»**, зелёный **«Нарушений не обнаружено»**. Цвет дополняют
подпись и значок; рядом с кадрами показано объяснение. Красный уровень не заменяет
решение человека. Ошибки, таймауты и незавершённая проверка имеют нейтральное состояние.

ML2 должен возвращать каждому событию `assessment: strong_evidence | needs_review`
и `assessment_reason`. Оба уровня используют прежний `verdict: violation`;
зелёный возможен только после успешного завершения с `no_violation` и пустым списком.
Старые события без уровня отображаются жёлтыми с честным пояснением об отсутствии
данных. Неизвестные уровни и противоречивые ответы отклоняются. Полный контракт —
`ml2/README.md` и `contracts/README.md`.

В списке демосценариев есть зелёный результат, одно красное событие, одно жёлтое
и смешанный набор (два красных + два жёлтых). Все прежние сценарии сохранены.
Оценки и демоправила вымышлены, помечены в интерфейсе и не добавлены в рабочий каталог.
Реальные модели эти уровни ещё не определяют в данном проекте.

Генератор `scripts/demo_video.sh [выходная_папка]` создаёт 12-секундный MOV из цветовых
таблиц и фигур. Людей, реальной кассы и реальных нарушений в нём нет; существующий файл
не перезаписывается. Можно переименовать копию в длинное имя для проверки интерфейса.
Демо выбирается отдельно от содержимого ролика; загрузка реальной записи не делает его
результаты настоящим анализом.

В деморежиме предусмотрены сценарии без событий, с одним/несколькими событиями,
с тремя кадрами, длинными описаниями, вымышленным источником, медленной обработкой,
ошибкой и некорректным ML-ответом. Проверяйте каждый сценарий синтетическим роликом.
Название выбранного сценария и режим должны оставаться видимыми в интерфейсе и API.
Multipart-параметр `demo_scenario`: `violation` (по умолчанию), `no_violation`,
`strong_evidence`, `needs_review`, `mixed_assessments`,
`multiple_events`, `three_frames`, `long_text`, `demo_rule`, `slow` (пауза 12 секунд),
`ml_error`, `invalid_ml_response`. Фиктивный каталог — `contracts/fixtures/demo-rules.json`;
источник `demo:interface-example` имеет `is_demo: true` и адрес на `example.invalid`.
Он отделён от `data/rules.json` и не является нормативом РК.

## Подключение ML1, ML2 и данных

1. **ML1:** реализовать локальный `POST /analyze`, передать воспроизводимый запуск,
   веса и явный ответ с обязательными `schema_version: "1.0"` и `events`.
   Пустой JSON и пропущенные обязательные поля
   не означают отсутствие событий. Осознанное отсутствие событий передаётся валидным
   ответом с пустым списком. Кадры должны декодироваться как JPEG; таймкоды находятся
   внутри длительности загруженного видео, дробная часть сохраняется.
   Обязательная версия и обязательный список — изменение старого контракта;
   прежний ответ без них нужно обновить, даже когда событий нет.
2. **ML2:** реализовать `POST /match` по согласованной схеме. **Сейчас ему передаются
   наблюдения и кадры от ML1, не исходный ролик.** Если модели понадобится сам ролик,
   сначала согласовать новый контракт и бюджет передачи. `rule_id` и сведения об
   источнике должны соответствовать каталогу; отсутствие подтверждения не маскирует
   ошибку сервиса.
3. **Данные и нормативы:** заполнить `data/rules.json` проверенными источниками и
   идентификаторами, предоставить разметку, критерии типов событий и проверочную выборку.
   Рабочий каталог намеренно не заполнен выдуманными законами.
4. **Frontend + Backend:** установить `PIPELINE_MODE=live`, `ML1_URL` и `ML2_URL`,
   перезапустить backend, проверить `/ready`, затем полный сценарий и ошибки моделей.

Схемы и примеры находятся в `contracts/`; инструкции участников — `ml1/README.md`,
`ml2/README.md`, `data/README.md`. Изменения контрактов нужно сверять именно с ними.
Все модели запускаются локально; облачные AI API не подключены. Получите и сохраните
веса до автономного запуска. Не добавляйте распознавание лиц или отправку записей
в сторонние AI-сервисы.

## Docker Compose

После создания `.env` (через setup либо вручную с отдельным случайным ключом):

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
```

Откройте <http://127.0.0.1:8000>. Compose собирает frontend с `npm ci`, Python с
`uv sync --frozen`, включает FFmpeg, запускает backend от непривилегированного
пользователя и отдаёт сайт с того же адреса. `.env`, локальные видео, БД, `node_modules`
и `.venv` исключены из контекста образа. Секрет передаётся только при старте контейнера.
Версии образов закреплены тегами; для побитового воспроизведения артефакта сохраняйте
построенный образ или дополнительно закрепите проверенные digest базовых образов.

SQLite и uploads хранятся в именованном томе `cashier_storage`, который переживает
`docker compose restart backend` и `docker compose down`. **`docker compose down -v`
удаляет данные**, поэтому не используйте его для обычного перезапуска. `data/`
подключена только для чтения; после изменения правил перезапустите backend.
Docker healthcheck проверяет доступность API; рабочую готовность проверяйте через `/ready`.

ML-контейнеры пока не объявлены: их образы и команды ещё должны предоставить участники.
В одной Compose-сети можно задать `ML1_URL=http://ml1:8001`, `ML2_URL=http://ml2:8002`
после добавления соответствующих сервисов. **127.0.0.1 внутри backend-контейнера
указывает на сам контейнер**, а не на ноутбук. Для моделей на macOS-хосте используется
`host.docker.internal` и доступный из Docker bind модели; на Linux адрес/сеть настраиваются
отдельно. Не открывайте ML-порты публично.

## Публичный HTTPS

Публичный сервис пока не развёрнут. Нужны предоставленные командой сервер и домен,
DNS-запись домена на адрес сервера, Docker/Compose и доступные входящие TCP 80/443.
Дополнительная конфигурация Caddy находится в `compose.https.yaml` и `deploy/Caddyfile`.

На сервере настройте приватный `.env`: задайте новый `API_KEY`, реальный `DOMAIN`
(только имя без `https://`), `ACME_EMAIL`, режим и адреса ML. Затем:

```bash
docker compose -f compose.yaml -f compose.https.yaml config --quiet
docker compose -f compose.yaml -f compose.https.yaml up -d --build
docker compose -f compose.yaml -f compose.https.yaml ps
```

Caddy получает сертификат для вашего домена и проксирует сайт/API на backend. Порт
8000 привязан к loopback сервера. По умолчанию тело ограничено 100 MiB + 1 MiB для
multipart, загрузка — 60 секунд, ожидание заголовка backend — 295 секунд, запись ответа —
300 секунд. При изменении `MAX_UPLOAD_MB` измените `PROXY_MAX_BODY_BYTES` по формуле
`MAX_UPLOAD_MB * 1024 * 1024 + 1048576`. Тело не буферизуется перед backend; повторная
отправка POST прокси не настроена. Документация: [лимит тела Caddy](https://caddyserver.com/docs/caddyfile/directives/request_body),
[параметры прокси](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy),
[таймауты сервера](https://caddyserver.com/docs/caddyfile/options#timeouts).

Не публикуйте `.env` и не задавайте `VITE_API_KEY`. Не передавайте ключ в URL, build args,
командах, скриншотах или логах. Не включайте логирование заголовка `X-API-Key` на прокси.
Ключ предназначен для авторизованного пользователя сайта; это общий доступ к API,
без отдельных учётных записей и разграничения результатов по пользователям.
Внешний HTTPS требует сети для сертификата; обработка видео после установки зависимостей
и весов не зависит от облачного AI.

## Проверки перед передачей

```bash
(cd backend && uv run --frozen pytest)
(cd frontend && npm test)
(cd frontend && npm run build)
bash -n scripts/setup.sh scripts/dev.sh scripts/demo_video.sh
docker compose config --quiet
```

Браузерные E2E-проверки:

```bash
(cd frontend && npm run test:e2e)
```

Нужны установленный Google Chrome (Playwright использует `channel: "chrome"`),
подготовленная `backend/.venv`, `ffmpeg` и `ffprobe` в PATH и свободные порты **8010/5174**.
Тестовый запуск создаёт синтетическое видео, отдельную SQLite и временные данные в
`work/e2e`, собирает отдельный production frontend и запускает свои backend/preview.
После проверки эти процессы останавливаются; основной сервер на порту 8000 не затрагивается.
Результаты этого запуска нужно читать в отчёте тестов; наличие команды не означает,
что браузерные проверки уже прошли на другом компьютере.

В браузере проверьте синтетическое видео, все демосценарии, обновление страницы в
обработке, восстановление результата, неверный ключ с последующим исправлением, 404
после удаления/истечения задачи, отключение сети и таймаут. На долгом сценарии
перезапустите backend: ожидается `failed`, а завершённая проверка должна сохраниться.
Проверьте несколько событий, увеличение 1–3 кадров, дробные таймкоды и переходы по
шкале; после обновления страницы повторно выберите локальный исходник. Проверьте
ширину ноутбука/телефона, Tab/Shift+Tab, Escape и reduced motion.

Для проверки очистки используйте отдельное тестовое `STORAGE_DIR` и короткие TTL/
интервал; не меняйте срок хранения пользовательских данных ради теста. Автотесты
проверяют контракты и жизненный цикл в изолированных временных каталогах.

До подключения настоящих ML1/ML2 не подтверждены точность обнаружения, полнота
нормативов, работа с реальными камерами, скорость на целевом железе и GPU-окружение.
Публичный домен/HTTPS и контейнерный запуск требуют отдельной проверки на сервере;
валидная Compose-конфигурация сама по себе не подтверждает сборку и запуск образа.
