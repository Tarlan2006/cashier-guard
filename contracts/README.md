# Контракты Cashier Guard, версия 1.2 (расширение API и новый статус отмены)

Владелец интеграции — участник 3. Источник типов: `backend/app/models.py`.
Из корня: `backend/.venv/bin/python scripts/export_contracts.py` обновляет JSON Schema.
OpenAPI: `/openapi.json`, документация API: `/docs`.

```text
Frontend → POST /api/v1/analyze → загрузка → очередь → FFprobe → FFmpeg
                                                        ↓ проверенный MP4 / H.264 / yuv420p
                                                   ML1 POST /analyze
                                                        ↓ наблюдения + JPEG
проверенный data/rules.json ───────────────────────→ ML2 POST /match
                                                        ↓ вердикт + rule_id
Frontend ← GET /api/v1/jobs/{job_id} ← SQLite ← проверка результата
```

## API сайта и жюри

Обязательные методы сохранены: `POST /api/v1/analyze` с multipart-полем `file`,
`GET /api/v1/jobs/{job_id}`. Для обоих нужен заголовок `X-API-Key`.
Поддерживаются MOV, MP4, AVI, MKV и WEBM. Расширение проверяется при загрузке,
реальный контейнер и видеодорожка — через FFprobe. Одного подходящего расширения
недостаточно. Ответ загрузки — HTTP 202 с `job_id`, `status`, `mode`.
Не передавайте ключ в URL или frontend-переменных сборки.

Статусы: `processing`, `done`, `failed`, `cancelled`. Этапы `stage`: `queued`, `preparing`,
`analyzing`, `matching`, `done`, `failed`, `cancelled`. Только `done` содержит окончательный
`verdict: violation | no_violation`. Ошибка ML, таймаут или перезапуск дают `failed`,
`verdict: null`, пустой список `violations`, безопасные `error` и `error_code`.
Этап `preparing` включает проверку содержимого, ожидание слота преобразования,
нормализацию и проверку выходного файла. Обязательные поля результата сохранены; отмена добавляет отдельный конечный статус.

Событие сохраняет поля задания: `type`, `timecode_sec`, `description`,
`evidence_frames` (1–3 объекта `{timestamp_sec, image_base64}`). Дополнительно —
`rule_id`, `rule`. Таймкоды передаются как числа в секундах, дробная часть сохраняется.
JPEG — чистая строка base64, без `data:image/jpeg;base64,`.

Дополнительные поля задачи (клиент должен допускать их отсутствие в старых ответах):

| Поле | Значение |
| --- | --- |
| `size_bytes` | Размер исходного файла; помогает повторно выбрать файл для предпросмотра |
| `duration_sec` | Длительность после подготовки видео |
| `source_time_offset_sec` | Необязательное конечное число: техническое начало шкалы исходного контейнера, может быть отрицательным; используется только для привязки локального предпросмотра к таймкодам результата |
| `timings_sec` | Измеренные секунды этапов `upload`, `queue`, `preparing`, `analyzing`, `matching`, `total` |
| `deadline_at` | UTC ISO 8601: абсолютный дедлайн текущей проверки |
| `completed_at` | UTC ISO 8601: время завершения |
| `expires_at` | UTC ISO 8601: срок удаления результата |
| `demo_scenario` | Выбранный тестовый сценарий в demo |
| `error_code` | Стабильный код ошибки в верхнем регистре |

HTTP-ошибки: 400 пустой файл; 401 неверный ключ; 404 неизвестная/удалённая задача;
408 таймаут загрузки; 413 превышение размера; 415 расширение; 422 некорректный запрос;
503 недоступность обработки, переполненная очередь или лимит хранения.
Сетевая ошибка клиента не равна `failed`: сервер может продолжать уже принятую задачу.
Клиент сохраняет текущий `job_id` и восстанавливает статус через GET.
Локальный `File`/Object URL после обновления страницы не восстанавливается. Для просмотра
сайт запрашивает защищённый архивный MP4 по отдельному маршруту. Если его срок истёк
или старое видео не было сохранено, можно выбрать исходник локально; результат и JPEG
доступны до собственного срока без видео.
`source_time_offset_sec` — совместимое дополнение к метаданным задачи; прежние
ответы могут его не содержать. Обязательные поля результата, статусы и контракты
ML1-ответа/ML2 не меняются.

## ML1: обязательный явный ответ

Локальный `POST /analyze`, multipart-поле `file`: имя **`video.mp4`**, MIME
**`video/mp4`**, MP4 с единственной видеодорожкой H.264 / `yuv420p`, без аудио.
Backend передаёт проверенный результат локальной нормализации, а не исходный контейнер.
Порядок и временные метки кадров сохраняются; фиксированный FPS не гарантируется.
Ориентация применяется к изображению; нечётные размеры дополняются до чётных без
обрезки или уменьшения разрешения. ML1 возвращает секунды на шкале исходного ролика.
Абсолютное начало контейнера приводится к нулю; относительная задержка начала
видеодорожки сохраняется, без добавления или удаления кадров. ML1 использует PTS
нормализованного файла и не вычитает первый PTS. `duration_sec` включает начальный
промежуток без изображения и заканчивается на конце видеодорожки; отдельный аудиохвост
исходника не добавляет кадры или время к этому входу. Схема ответа остаётся `ml1-response.schema.json`.
Успешный ответ без наблюдений должен быть именно:

```json
{"schema_version": "1.0", "events": []}
```

`schema_version` и `events` теперь обязательны: `{}`, `null`, пустое тело, пропущенное
поле и неизвестная версия **не означают отсутствие событий** и завершают задачу ошибкой.
Это намеренное ужесточение прежнего контракта, где оба поля имели значения по умолчанию.

У каждого наблюдения обязательны `id`, `start_sec`, `end_sec`, `description`,
`evidence_frames`. `id` уникален в ответе. Интервал упорядочен:
`0 ≤ start_sec ≤ end_sec ≤ duration_sec`, причём `start_sec < duration_sec`.
Все числовые значения конечны: NaN/Infinity запрещены.

## ML2: наблюдения и кадры, без исходного видео

Локальный `POST /match`, JSON по `ml2-request.schema.json`:
`schema_version`, `duration_sec`, `events`, `rules`.

**Сейчас ML2 получает только наблюдения ML1, выбранные JPEG-кадры и каталог правил.
Исходный ролик и дополнительные фрагменты этому сервису не передаются.** Если будущей
модели нужен ролик, согласуйте изменение контракта до подключения; backend не предполагает
такого требования за разработчика модели.

Ответ по `analysis-result.schema.json`: `verdict` и список `violations`.
Для явного отсутствия нарушений передавайте `{"verdict":"no_violation","violations":[]}`.
Оба поля обязательны: отсутствие списка не означает отсутствие событий. Пустой ответ
или ответ без `verdict` отклоняется. `violation` требует непустого списка.
Каждое событие в live обязано иметь известный `rule_id` из переданного каталога.
Backend добавляет `rule` самостоятельно. Если ML2 прислал `rule`, его содержание
должно полностью совпадать с каталогом: подмена текста или URL отклоняется.

### Уровни событий и общий результат

Каждое новое событие ML2 должно содержать `assessment` и `assessment_reason`:

| Значение | Подпись | Требования |
| --- | --- | --- |
| `strong_evidence` | Явные признаки нарушения (красный) | Убедительные визуальные доказательства, непустое объяснение; в live — проверенное правило из каталога и валидные JPEG |
| `needs_review` | Требует уточнения (жёлтый) | Неоднозначное событие, которое должен проверить человек; объяснение указывает причину неопределённости |

Оба уровня относятся к `verdict: "violation"`. `assessment_reason` — текст,
не процент уверенности. Frontend только отображает переданный уровень и агрегирует
события: хотя бы одно `strong_evidence` → красный; непустой список только
`needs_review`/старых событий → жёлтый; только успешный `done` + `no_violation` + `[]`
→ зелёный «Нарушений не обнаружено». Карточки сохраняют свои цвета при смешанном
результате; интерфейс показывает количество событий каждого уровня.

Отсутствующий/null `assessment` сохраняется как отсутствие данных и отображается
жёлтым с явным пояснением. Отсутствующее/null объяснение не придумывается.
Неизвестный уровень, неверный тип, пробельное объяснение и `strong_evidence` без
объяснения — ошибки контракта. Опциональность полей в схемах нужна для старых
ответов/SQLite, а не для новых реализаций ML2. JSON-экспорт сохраняет переданные поля.

Красный уровень не означает окончательно подтверждённое нарушение: решение принимает
человек. Ошибки, таймауты и незавершённые задачи — нейтральная «Проверка не завершена».
Повреждённый сохранённый результат становится `failed` / `RESULT_INVALID` с `verdict:null`,
а не зелёным ответом. Схема запроса ML2 и вход ML1 не меняются.

## Валидация доказательств и правил

- На событие 1–3 настоящих JPEG; до 4 000 000 символов base64 на кадр.
- Pillow проверяет формат, структуру и полностью декодирует изображение. Поддельные
  JPEG-маркеры, PNG, обрезанные файлы и изображения более 8 млн пикселей либо
  более 8192 пикселей по стороне отклоняются.
- Время каждого кадра и `timecode_sec` результата: `0 ≤ t < duration_sec`.
- До 100 событий/наблюдений в ответе. Ответ каждого ML-сервиса ограничен 32 MiB;
  чтение потоковое с проверкой фактически полученного размера.
- `data/rules.json`: объект `rules` (до 5000), необязательная для совместимости
  `schema_version: "1.0"`. Идентификаторы уникальны, строки и `visual_signs` непустые,
  URL абсолютный HTTP(S), без учётных данных. Размер каталога до 4 MiB.
- Каталог для live должен быть непустым и проверенным участником 4. Поле `is_demo`
  необязательное, по умолчанию `false`; записи с `true` и ID с префиксом `demo:`
  запрещены в рабочем каталоге. Backend проверяет структуру, но не устанавливает
  юридическую применимость документа и не доказывает подлинность кадра — это задача
  разметки и независимой оценки качества.

`data/rules.json` намеренно не заполнен: реальные нормативы ожидаются от участника 4.

## Бюджет, сохранение и готовность

По умолчанию `JOB_TIMEOUT_SECONDS=290`, максимум 295 секунд. Отсчёт начинается
при получении HTTP-запроса backend: включает загрузку, очередь, FFprobe, ожидание
преобразования, FFmpeg, проверку выходного файла и оба ML-этапа.
Загрузка дополнительно ограничена `UPLOAD_TIMEOUT_SECONDS=60` и остатком общего времени.
HTTP-запрос каждого ML: connect/pool 5 с, write 30 с, read 90 с, весь запрос до 120 с.
Общий дедлайн имеет приоритет; медленная отправка отдельных байтов не продлевает его.
Пять минут от действия в браузере также зависят от сети до backend и внешнего прокси.

SQLite сохраняет статусы и результаты. Незавершённая при перезапуске задача переходит
в `failed`/`SERVER_RESTARTED`; её требуется загрузить заново. Исходник удаляется после
обработки, нормализованный MP4 успешной проверки сохраняется отдельно в `storage/videos/`.
При ошибке или отмене удаляются обе временные копии; остатки очищаются после перезапуска.
Результат, JPEG и решения хранятся `HISTORY_TTL_HOURS` (720 часов),
видео независимо — `VIDEO_TTL_HOURS` (168 часов). Автоочистка каждые
`CLEANUP_INTERVAL_SECONDS` (60 с). После удаления результата GET возвращает 404;
истечение только видео даёт 410 на его отдельном маршруте и сохраняет результат.

`GET /api/v1/health` проверяет работу backend без ключа. `GET /api/v1/ready` отдельно
проверяет готовность обработки: FFmpeg/FFprobe, каталог и достижимость ML-сервисов
в live. TCP-достижимость не подтверждает загрузку весов или правильность модели.
В demo каталог и ML-сервисы для обработки не нужны.

Коды ML-ошибок: `ML1_INVALID_RESPONSE`, `ML2_INVALID_RESPONSE`, `ML1_UNAVAILABLE`,
`ML2_UNAVAILABLE`, `ML1_TIMEOUT`, `ML2_TIMEOUT`, `ML1_HTTP_ERROR`, `ML2_HTTP_ERROR`,
`ML1_INVALID_TIMECODE`, `ML2_INVALID_TIMECODE`, `ML2_UNKNOWN_RULE`, `ML2_RULE_MISMATCH`.
Также: `RULES_EMPTY`, `RULES_INVALID`, `VIDEO_INVALID`, `FRAME_INVALID`, `TIMEOUT`,
`SERVER_RESTARTED`, `RESULT_INVALID`. Тела ответов ML, изображения и исключения с секретами не выдаются клиенту.

Ошибки подготовки: `VIDEO_NO_VIDEO_TRACK`, `VIDEO_CODEC_UNSUPPORTED`,
`VIDEO_DURATION_INVALID`, `VIDEO_CONVERSION_FAILED`, `VIDEO_TIMELINE_UNSUPPORTED`,
`VIDEO_ORIENTATION_UNSUPPORTED`, `VIDEO_STORAGE_LIMIT`, `STORAGE_FULL`,
`FFMPEG_UNAVAILABLE`. Они не вызывают ML1/ML2 и не дают вердикт об отсутствии нарушений.
Подготовка ограничена `NORMALIZATION_WORKERS` (по умолчанию 1) и `MAX_NORMALIZED_MB`
(512 MiB), свободным диском и общей квотой `MAX_STORAGE_MB`.

## Явные демонстрационные сценарии

Только для тестов при `PIPELINE_MODE=demo` передайте multipart `demo_scenario`. В пользовательском интерфейсе запуск демопроверки отсутствует:

| Значение | Результат |
| --- | --- |
| `no_violation` | Зелёный деморезультат без событий |
| `strong_evidence` | Одно красное событие с вымышленным обоснованием и демоправилом |
| `needs_review` | Одно жёлтое событие с вымышленным объяснением |
| `mixed_assessments` | Два красных и два жёлтых события с индивидуальными уровнями |
| `violation` | Одно искусственное событие, значение по умолчанию |
| `multiple_events` | Три события в разных местах видео |
| `three_frames` | Одно событие с тремя JPEG |
| `long_text` | Длинные название и описание; используйте синтетический файл с длинным именем |
| `demo_rule` | Событие с помеченным вымышленным источником |
| `slow` | Искусственная пауза 12 секунд для проверки восстановления страницы |
| `ml_error` | `failed`, `ML1_UNAVAILABLE` |
| `invalid_ml_response` | `failed`, `ML1_INVALID_RESPONSE` через тот же валидатор, что в live |

В live выбор demo не меняет результат моделей. Во всех demo-сценариях события заданы
искусственно, а кадры извлекаются из **нормализованной копии загруженного** видео. Используйте синтетические
ролики из `scripts/demo_video.sh`; загрузка настоящей записи не превращает demo в анализ.
Сайт должен сохранять видимую отметку деморежима на всём пути.

Только `contracts/fixtures/demo-rules.json` содержит вымышленный источник:
`demo:interface-example`, `is_demo: true`, домен `example.invalid`.
Он не является нормативным актом и никогда не объединяется с `data/rules.json`.


## История и решения

Все методы ниже требуют **X-API-Key** в заголовке. Ключи в query string не принимаются.
История общая для обладателей серверного ключа; это не авторизация отдельных сотрудников.

| Метод | Путь | Контракт |
| --- | --- | --- |
| GET | `/api/v1/jobs` | `history-page.schema.json` |
| DELETE | `/api/v1/jobs/{job_id}` | `{deleted: true, job_id}`; удаляет результат, решения и MP4 |
| GET | `/api/v1/jobs/{job_id}/video` | защищённый `video/mp4`, Range/206; 410 если видео недоступно |
| PATCH | `/api/v1/jobs/{job_id}/events/{event_id}/review` | тело `event-review-update.schema.json`, ответ `human-review.schema.json` |
| GET | `/api/v1/analytics` | `analytics-response.schema.json` |

Параметры списка: `page` (с 1), `page_size` (1–100, по умолчанию 20), `search` (до 255
символов, буквальное вхождение с Unicode casefold), `status` (processing/done/failed/cancelled),
`mode` (live/demo), `category_id`, `date_from`, `date_to`. Сортировка: created_at DESC,
job_id DESC. `date_from` включается, `date_to` исключается; обе ISO datetime с часовым
поясом. При некорректном периоде — 422. Аналитика принимает такие же границы периода,
считает по created_at, только done/live, только ещё хранящиеся результаты. GET не меняет
счётчики или решения. DELETE processing и PATCH незавершённой задачи дают 409.

События **JobResponse**, а не ответа ML2, расширены `event_id`, `category_id`,
`human_review: {decision, comment, updated_at}`. Изначально decision=unreviewed,
comment пустой, updated_at=null. PATCH допускает только decision и comment (до 4000),
лишние поля отвергаются. ML assessment/reason/rule/JPEG неизменны; решение хранится отдельно.
Старые события получают устойчивые ID при миграции. Категории вычисляются от точного
контрактного type, без догадок и нормализации формулировок. Красный count означает
strong_evidence; жёлтый включает legacy без assessment, сохраняя непереданный уровень.

Задача также возвращает video_available, video_expires_at, video_size_bytes и
video_unavailable_reason (expired/missing/not_retained). Последний применим к старым
результатам, для которых видео никогда не архивировалось. Исчезновение видео не меняет
ML verdict и не удаляет JPEG/решения. История и аналитика передают только счётчики,
не копии base64-кадров. Три кадра у события считаются одним событием.

Новая история хранится HISTORY_TTL_HOURS (по умолчанию 720), MP4 — VIDEO_TTL_HOURS
(168). Часовой RESULT_TTL_HOURS заменён независимыми настройками. Общая дисковая квота
и лимит числа записей сохраняются; превышение места — 503. Старые строки SQLite при
первой миграции получают новый срок, уже физически удалённые данные не восстанавливаются.
Неполный ответ ML, помеченный partial/incomplete или X-Analysis-Complete=false, не считается
успешным и не входит в аналитику. Деморезультаты в основной аналитике всегда исключены.

## Пакетная отправка, отмена и очередь рассмотрения (API 0.4, схемы 1.2)

Существующие ML1/ML2-схемы не меняются. В JobResponse/HistoryItem добавлен конечный
статус `cancelled` и stage `cancelled`: клиентам нужно поддержать это значение.
Отменённая задача имеет `verdict: null`, `violations: []`, `error_code: CANCELLED`,
completed_at и обычный срок хранения результата. Она исключена из аналитики,
как failed/processing/demo. Только done/live попадает в успешную статистику.

Все методы ниже используют тот же заголовок **X-API-Key**, включая PDF и журнал.
Ключ авторизации никогда не передаётся в URL. OpenAPI `/docs` содержит параметры.

| Метод | Путь | Поведение |
| --- | --- | --- |
| POST | `/api/v1/analyze` | Прежний один файл `file`, дополнительно multipart `tags` = JSON-массив строк; необязательный заголовок `Idempotency-Key` |
| GET | `/api/v1/submissions/{request_key}` | JobResponse принятой отправки; 404 если ключ не найден/истёк |
| POST | `/api/v1/jobs/{job_id}/cancel` | JobResponse фактического состояния; завершённая задача не отменяется задним числом |
| PATCH | `/api/v1/jobs/{job_id}/tags` | tags-update.schema.json → `{tags: [...]}` |
| GET | `/api/v1/jobs/{job_id}/report.pdf` | Приватный application/pdf, no-store; не запускает ML и не сохраняет файл на сервере |
| GET | `/api/v1/jobs/{job_id}/review-log` | review-log.schema.json, page/page_size (1–100); новые записи первыми |
| GET | `/api/v1/review-queue` | review-queue.schema.json; непроверенные события из хранящихся done-задач |
| GET | `/api/v1/review-queue/options` | Точные category_id/type и метки для фильтров |

Idempotency-Key: 16–100 символов `[a-zA-Z0-9_-]`, случайный UUID на одну отправку.
Ключ связан с SHA-256 содержимого файла, имени, исходных меток и demo-сценария
(только в demo). Повтор того же запроса возвращает существующий job_id, включая
завершённый/отменённый, без нового анализа. Изменённое содержимое с тем же ключом —
409. Метки, позднее отредактированные через PATCH, повтор отправки не переписывает.
Без заголовка прежнее поведение сохраняется. После удаления/истечения результата
удаляется и привязка отправки. GET /submissions позволяет восстановить потерянный
ответ POST; сам request_key не является ключом авторизации.

Пакетный интерфейс ограничивает список десятью файлами и двумя одновременными
отправками. Каждый запрос проходит прежние ограничения формата, размера, длительности,
дедлайна, диска, очереди и параллельности backend. Ошибка одного не останавливает другие.
В sessionStorage хранятся ID отправок/заданий и метаданные списка, но не File и не JPEG.
После обновления принятые задания запрашиваются через GET. Для непринятого файла
нужно повторно выбрать тот же файл; повтор использует прежний ключ. POST не повторяется
автоматически. Отмена во время HTTP-загрузки ожидает её ответа и затем отменяет
принятое задание; при потере ответа состояние уточняется по ключу отправки.

Отмена сначала атомарно сохраняет cancelled, затем отменяет asyncio-задачу и её
управляемые операции. FFmpeg/FFprobe убиваются и reap выполняется существующим
media.command. Задание в очереди пропускается worker-ом. Поздний результат и stage
не могут переписать cancelled. HTTP-запрос к внешней модели закрывается; отдельный
внешний сервис может продолжать вычисления, пока не поддерживает собственную отмену.
Остальные worker-ы и задания продолжают работу. При ошибке сохранения отмены — 503,
без ложного подтверждения. После успешного сохранения она переживает перезапуск.

Метки: до 10 непустых строк по 64 символа, пробелы по краям удаляются, точные дубликаты
исключаются. `GET /jobs` принимает дополнительный точный `tag`. Метки доступны в
JobResponse, HistoryItem, очереди и PDF; хранятся отдельно от ML JSON.

Очередь: page≥1/page_size 1–50, date_from/date_to с прежними включённым началом и
исключённым концом по created_at, точный category_id, точный tag. Demo явно помечены.
`total` — число непроверенных; `total_events` — все события по этим фильтрам;
`reviewed_events` — confirmed+rejected по тем же фильтрам. Считаются события, не JPEG.
`exclude_event_id` исключает текущее событие только из возвращаемого списка для перехода
«Следующее непроверенное»; прогресс не меняет. Открытие/переход — только GET.

PATCH решения атомарно обновляет прежнюю таблицу events и добавляет review_log с
previous/current, UTC changed_at, устойчивым event_id и origin=review. Повтор абсолютно
того же решения/комментария не создаёт искусственную запись. Журнал только добавляется;
автора по общему API-ключу определить нельзя. Миграция v2→v3 сохраняет текущие решения
и добавляет origin=migration_snapshot для существующего решения с updated_at; это
снимок, не восстановленная история ранних изменений. Изменение решения пересчитывает
тот же источник данных для истории, очереди, PDF и аналитики.

PDF содержит сохранённые метаданные, полноту/режим, события, таймкоды, кадры, объяснения,
реальные предоставленные ссылки и текущие решения/комментарии. Demo-источники не
выдаются за нормативы; актуальная HTTP-доступность сохранённых ссылок не проверяется.
Недоступное видео/кадры/правило явно обозначены. Встроенный DejaVu Sans обеспечивает
кириллицу; длинный текст переносится, страницы нумеруются. Отчёт доступен пока доступен
результат, даже после истечения видео. Формируется по одному, при занятости — 503;
ошибка формирования не удаляет результат. Даты PDF имеют явный UTC.

Сроки не меняются: результат, JPEG, метки, решения, журнал и ключи отправок удаляются
вместе по HISTORY_TTL_HOURS; архив — независимо по VIDEO_TTL_HOURS. Миграция v3 не
продлевает сроки v2. Журнал/метки учитываются в существующей квоте SQLite. Черновики
решений в текущей вкладке: sessionStorage, максимум 50, до 24 часов или срока результата,
удаляются после успешного сохранения; закрытие вкладки очищает их. Список пакетной
отправки можно очистить отдельно, не удаляя историю.
